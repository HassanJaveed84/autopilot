## 4. Defect investigation

The method: each problem was traced through the stored exchanges, the prompts actually sent, the production code at `6d3a70b`, and an offline replay of the two recorded replies through the real parser, merge, assessor and composer (`LiveRunRegressionTest`, `LiveRunServiceReplayTest`). The replay reproduces the stored record exactly, for example c1's final support `[2, 11, 3, 6, 12]` and the stored status reasons.

### A. False missing-source limitation: confirmed defect

The full path:

1. **GATHER evidence.** c1 cited `unionstationdc.com/contact-us` through a real provider citation. The source registry stored it as source 1 (`citedCount 1`, verbatim quote kept).
2. **The FILL_GAPS prompt** listed it as "s1 · Contact Us · unionstationdc.com" under "Sources already held". It did not say which held evidence belonged to which claim, why c1 was still open (the undated-window reason) or that held evidence would be kept. The model could not cite s1 again, because its new search did not return the page and citations come only from a call's own results. It wrote, accurately about its own call, "I did not retrieve … in this search".
3. **Aggregation.** `TurnWork.merge` replaced a re-checked claim's support with the new block's support whenever the block brought new sources (the RES-106 rule meant for re-checking inherited findings). Inside a single turn, that discarded source 1 and the GATHER AGAINST line. The final c1 no longer contained the issuer's page.
4. **The answer.** `merge` replaced the turn's answer with the later call's ANSWER, and `AnswerComposer` passed the lead through untouched. Nothing distinguished a statement about one call ("in this search") from a statement about the investigation.

So: the later stage did omit earlier evidence (a merge defect). The model's sentence was true of its own call but false of the turn, which is a prompt-contract gap. And the composer had no rule to reject call-scoped narration, which is a composition defect.

**Fixes (general):**

- **Merge:** when a later call in the same turn restates the same statement (same text, or the same values reworded), the evidence the turn already gathered is kept. A restatement of the same source replaces its earlier line. Re-checks of findings inherited from earlier turns still stand as written (RES-106). A changed value is a new statement and carries no earlier evidence.
- **Composer:** in an answer written by any call after the first, sentences that narrate that call's own search ("this search", "these results", "this pass" and similar) are left out. Every real gap still reaches the person, because each load-bearing claim that is not established becomes a caveat from the evidence and unresolved items are kept. A later call's unresolved note that is about re-citing a source the turn already holds is dropped.
- **Prompt v3:** for each open claim, the FILL_GAPS prompt now gives the reason it is open and the held evidence (source number, kind, dated or undated). It states that held evidence stays with its claim, forbids saying a held source was not retrieved, found or cited, and requires any rewritten ANSWER to cover the whole investigation.

### B. `official=false` on every source: harmless metadata, documented and not changed

`SourceRegistry` sets `official` from `Sources.tier(url)`, a suffix registry of government hosts (`.gov`, `.gov.uk` and similar; brand names never qualify). `unionstationdc.com` and `amtrak.com` are not government hosts, so `false` is the correct value of that field. It is not a failed extraction or a misclassification.

| Question | Answer |
|---|---|
| Does it affect sufficiency? | Only as a fallback for evidence `kind` when a reply states none: a government host then defaults to `primary`. Every line in this run stated a kind, so `official` affected nothing. `LiveRunRegressionTest.nonGovernmentHostsAreNotOfficialAndSufficiencyFollowsTheStatedKind` pins this. |
| Is it shown? | The Investigation Thread does not display it. It is kept for the M3A.2 read-only screens. |
| Why does it disagree with PRIMARY? | They measure different things. `kind` is the reply's statement about a source's role for one claim (the issuer or operator of a fact), and it is per claim. `official` is a property of the host. A station operator's `.com` page can be the primary source for its own address without being a government host. Equating the two in either direction would treat domain ownership as authority. |

The remaining risk is that `kind=primary` is a model-supplied label the code cannot verify. It can only raise sufficiency through the issuer route, so mislabelling is a live-evaluation risk (§7).

### D. c2's scope reason: confirmed (malformed evidence metadata, reported as fact)

The reply's EVIDENCE line for c2 was `(kind=secondary · asof=- · about=Wikipedia article on Columbus Circle)`. The parser read it correctly. `EvidenceAttrs.split` correctly found that the label differs from the claim's scope ("Station location relative to Columbus Circle"), so the row became off-scope, and the assessor rated c2 NOT_ESTABLISHED.

The page is in fact about the claim's subject: the model used `about=` to describe the page, not to name another scope. It did the same in GATHER for c1's Amtrak and Wikipedia rows, which cost c1 its Amtrak evidence at that point.

So this is not a parsing defect, and not a bad comparison. The mismatch rule ("any `about=` that differs from the scope makes the row off-scope") is broad by design, because the label can only lower a status. The two defects are the model-supplied label (a prompt-contract ambiguity) and a reason that stated the label as a verified fact: "The source found is about Wikipedia article on Columbus Circle, not …".

**Fixes:** prompt v3 says `about=` names only another scope (variant, place, population, seller or period) and is never a description of the page, its publisher or its format. The reason now reports the label as a label: "Its only source was marked as being about something else (…), so it does not count for …". No status is upgraded. A heuristic that ignored `about=` labels resembling page descriptions was rejected, because it would also accept real variant mismatches (for example "Bleu de Chanel Parfum" against "Eau de Toilette").

### E. Unnecessary second stage: confirmed defect (freshness rule)

Of the explanations the owner listed:

- It was **not** that the first result lacked required evidence. The issuer's contact page, in scope and stating the address, settles a `needs=direct` fact.
- It was **not** a missing derivation. Statuses are derived after every call.
- It was **not** c2. Non-load-bearing claims never hold a turn open.
- It was **not** a fixed stage sequence. FILL_GAPS runs only while a load-bearing claim is open, and it is skipped otherwise.

The cause: `ClaimAssessor.fresh` returned false for any claim with a freshness window (`fresh=1y`) whose evidence carried no date, even when the claim was marked `volatile=no`. A stable fact on an undated page was therefore "only indicated", c1 stayed open, and FILL_GAPS was correctly triggered by a wrong status. The model then made it pass by stamping the claim `asof=2026-10`, the month of the run.

Did the second stage improve anything? No. It added five secondary pages and one disagreeing outlier to a fact the issuer's page already settled. It lost the issuer's page (A) and introduced the false limitation (A), the leaked id (Leakage) and the paraphrase with an unsupported addition (C). Its cost was $0.04214, 44% of the run.

**Fix:** undated evidence for a stable claim is current while it was read within the claim's own window. Volatile claims still need the fact's own date (RES-046 unchanged), and stable evidence read longer ago than its window is still only indicated, with a reason saying when it was last read.

The stopping rule itself (skip FILL_GAPS when no load-bearing claim is open) needed no change. Replaying this run's replies through the real service now makes one call and one search: FILL_GAPS is skipped because every load-bearing claim is established, and c1 is established as "The issuing source, in scope".

## 7. Remaining live-evaluation risks

1. **Prompt v3 is unverified live.** Whether the model now uses `about=` only for another scope, and whether it stops narrating its own search, can only be seen in a live run.
2. **Model-supplied labels still decide status.** `kind=primary`, `volatile`, `fresh=` and `asof=` cannot be checked against the page. A model that marks a volatile fact `volatile=no`, or calls an aggregator primary, can overstate a claim. The R-C, R-E and R-K scenarios exercise this.
3. **Origin independence is host-based (G).** Two sites from one publisher still count as two for `needs=corroborated`. A lower-only "same publisher as sN" signal is a candidate.
4. **An unestablished side claim can sit in the lead unqualified (I).**
5. **R-N(b) depends on the provider objective pass.** Local preparation treats only a missing subject as ambiguous. With the provider pass off (the default in the app and in the harness), "address of Union Station" with no city would be marked established and offered for authorization. Before R-N(b) is spent on, the harness needs the provider pass enabled for that scenario (one no-search call to the cheapest model, under general consent), or the product needs a decision on the local path.
6. **Stage 1 needs two runs per scenario.** This was run 1 of 2 for R-N(a).
